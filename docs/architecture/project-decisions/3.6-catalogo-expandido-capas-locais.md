# Decisão 3.6 — catálogo acadêmico com capas locais

**Data:** 21/11/2026. **Responsável:** Aria (@architect).  
**Story:** `docs/stories/3.6.catalogo-expandido-capas-locais.md`.  
**Estado:** aceita para implementação com as condições abaixo; testes e gate QA pendentes.

## Dados e apresentação

Os dois produtos originais mantêm IDs, preços, campos e vínculos históricos. Uma fonte JSON compartilhada define os 30 novos jogos fictícios, com preço inteiro em centavos, IDs estáveis e referências às plataformas existentes. Cliente e carga do SQLite derivam dessa mesma fonte; testar equivalência de domínio, sem depender da ordem do catálogo. O bootstrap efetivo do banco passa a ser o SQL atual mais a aplicação transacional do manifesto; documentar essa composição como fonte da seed ampliada, em vez de manter duas listas divergentes de 30 produtos.

As 32 capas serão PNGs locais originais, gerados por script determinístico de pixel art com Node/zlib, sem dependência nova. Cada ID tem `require` estático no mapeamento do componente de capa. Isso conserva resolução offline e empacotamento pelo Metro sem acrescentar URL de imagem à API, banco, exportação ou outbox. Produtos administrativos não presentes no mapeamento e erros de carregamento recebem fallback local; mudar de produto deve reiniciar o estado de falha. O componente fornece proporção estável, nome acessível e dimensões que não ampliem a largura do card. Compatibilidade cloud permanece demonstrativa, sem alegação comercial.

## Banco existente e inicialização

Um helper aditivo usa o manifesto para inserir apenas IDs novos; nunca executa atualização ou substituição de produto existente. Insere compatibilidades somente para produto efetivamente criado pelo helper: encontrar um ID já existente não autoriza acrescentar plataformas nem restaurar uma relação removida pelo usuário. A operação deve ser transacional, com rollback integral em erro e sem tocar em pedido, pagamento, biblioteca, chaves ou usuário.

Em banco novo, `initializeDatabase` aplica o helper antes da validação de FKs e publicação do arquivo, preservando as 13 tabelas de domínio iniciais. Na abertura pela API, uma marca operacional de migração identifica a edição do catálogo. Verificar a marca, aplicar os inserts e registrar conclusão na mesma transação; uma falha não grava conclusão parcial. A marca impede que produto excluído após a migração reapareça em inicializações seguintes. Não usar apenas `INSERT OR IGNORE` em todo startup: isso ressuscitaria exclusões. A marca operacional não integra o modelo de domínio acadêmico.

Preservar também quando um dos novos IDs já pertencer a produto customizado: mantê-lo integralmente e considerar esse conflito como dado existente, sem overwrite. Não reintroduzir os dois originais caso tenham sido legitimamente removidos. `npm run db:init` continua sendo reconstrução explícita e destrutiva do banco de demonstração; não deve ser usado para atualizar uma instalação existente. Bancos novos recebem a marca no primeiro startup da API; esse bootstrap não promete detectar exclusões externas ocorridas entre a criação direta do arquivo e sua primeira abertura pela API.

## Cache e pendências

Manter snapshot `version: 2` e acrescentar marcador opcional `catalogEdition: 2`, preservado pelo sanitizador e por todas as atualizações. Só habilitar expansão quando `initialProducts` contiver a massa completa reconhecida pelo manifesto; não inferir isso apenas pelo tamanho 32 nem alterar fixtures menores silenciosamente.

No primeiro load sem marcador, acrescentar somente os 30 IDs do incremento ausentes do catálogo **e ausentes das operações pendentes**. Uma exclusão na outbox é intenção explícita: não recolocar esse ID. IDs existentes preservam exatamente sua edição local. Não restaurar os dois originais, substituir arrays pessoais, alterar carrinho/pedido/biblioteca/checkout, retirar `catalogDirty`/`legacyDirty`, reordenar outbox ou inventar operações remotas de criação dos itens-base. A expansão local corresponde ao bootstrap do servidor, não a CRUD do administrador.

Persistir catálogo e marcador juntos antes de publicar o novo estado. Falha de escrita conserva o snapshot anterior; repetição tenta a mesma migração sem duplicar. Se o marcador já existe, não completar novamente IDs ausentes, inclusive após refresh/descarte, exclusão sincronizada, reload ou reinício. A API continua sendo autoridade na atualização explícita: catálogo remoto não deve ser unido permanentemente ao manifesto. Dados customizados/conflitos podem resultar em quantidade diferente de 32 e isso não é motivo para reset ou exclusão.

## Validação e limites

Os testes atuais podem manter fixtures isoladas de dois produtos para seus contratos históricos: o harness deve marcar explicitamente a edição do cache e preparar o banco reduzido somente no ambiente de teste, após o bootstrap operacional. Nenhuma flag de produção deve reduzir a massa-base. Manter novos testes com bootstrap real de 32 produtos para evitar que fixtures escondam divergências.

Cobrir: 32 IDs únicos/equivalência, preços e relações dos originais, edição de novo ID antes da migração, repetição, exclusão depois da marca, rollback, cache limpo/sujo/legado, DELETE pendente, marker preservado após refresh e fallback de imagem. E2E real deve percorrer os 32 IDs e verificar imagens efetivamente carregadas, filtros, detalhe, carrinho e alcance do último item em 320/390 px. PNG presente no filesystem ou `require` resolvido não comprova carregamento visual. Regressão, lint, typecheck, build e QA permanecem obrigatórios; execução web não comprova dispositivo nativo.
