## Story

**Como** equipe de desenvolvimento do PixelVault,  
**quero** converter o modelo relacional aprovado em scripts SQL e em uma base SQLite local recriável por comando, com poucos dados fictícios,  
**para que** o esquema, as relações e as consultas essenciais possam ser demonstrados e testados antes da API Node.

## Contexto e valor

Esta story materializa o Prompt 14 e a parcela de banco de dados de `HT-02`. Ela depende do modelo lógico aprovado no Prompt 13 e mantém coerência com os dados e comportamentos reais do Prompt 12. O incremento deve funcionar integralmente por CLI, produzir uma base local descartável e evidências reais, sem conectar o aplicativo Expo ao banco e sem antecipar endpoints, Express ou a fronteira de pagamento reservados ao Prompt 15.

O identificador `2.2` representa o segundo incremento da Fase 5: o Prompt 13 (`2.1` lógico) foi concluído no artefato `documentos/PixelVault_Modelo_de_Dados_e_DER.md`, ainda que não exista uma story `2.1` local. Esse artefato declara explicitamente o modelo como entrada aprovada para o Prompt 14.

## Acceptance Criteria

1. Existe um script SQL de esquema, executável no SQLite, que cria exatamente as 13 tabelas aprovadas no Prompt 13: `usuario`, `loja_ativacao`, `plataforma_cloud`, `produto`, `compatibilidade_produto`, `carrinho`, `item_carrinho`, `pedido`, `item_pedido`, `pagamento`, `biblioteca`, `item_biblioteca` e `chave_ativacao`; nenhuma tabela sem uso no escopo é adicionada.
2. O esquema usa identificadores textuais, valores monetários em centavos inteiros e implementa as colunas, tipos, chaves primárias, chaves estrangeiras, nulabilidade, unicidades e `CHECK` definidos no dicionário aprovado. `item_pedido` adota um `id` técnico textual como PK e mantém `UNIQUE (pedido_id, produto_id)`; `item_biblioteca.item_pedido_id` referencia esse identificador de forma única.
3. A conexão de inicialização e cada conexão de teste habilitam `PRAGMA foreign_keys = ON`. FKs históricas de `usuario`, `produto` e `pedido` usam comportamento restritivo; dependentes transitórios usam `CASCADE` somente quando isso estiver alinhado às regras do Prompt 13. Índices explícitos cobrem FKs usadas nas consultas demonstrativas quando não estiverem cobertas por PK ou `UNIQUE`.
4. Restrições diretamente representáveis em SQLite são comprovadas por testes negativos, incluindo pelo menos: e-mail duplicado, papel de usuário inválido, tipo/preço de produto inválido, item duplicado no carrinho, FK inexistente, pagamento duplicado para o mesmo pedido, item de biblioteca duplicado e chave repetida.
5. Regras que exigem validação entre múltiplas tabelas — produto com ao menos uma compatibilidade, total do pedido igual à soma dos itens, valor do pagamento igual ao pedido e inserção na biblioteca somente após pagamento aprovado — são documentadas como invariantes transacionais para o Prompt 15 e são respeitadas pela massa fictícia; não são criados triggers ou comportamentos de API não aprovados apenas para simular essa camada.
6. Existe um script de massa fictícia separado do esquema e pequeno o suficiente para inspeção, contendo os dois usuários acadêmicos (jogador e administrador), uma loja de ativação fictícia, GeForce NOW, Boosteroid, `Orbit Raiders` (`JOGO`, 7.990 centavos) e `Neon Expansion` (`DLC`, 2.490 centavos), com as compatibilidades usadas no Prompt 12. Nenhuma senha em texto puro, dado pessoal real, dado de cartão ou chave comercial válida é persistido.
7. A massa contém um cenário pós-compra coerente e transacional: um pedido fictício do jogador com os dois produtos, dois snapshots de preço, total de 10.480 centavos, um pagamento fictício `APROVADO` de igual valor, biblioteca do mesmo usuário, dois itens sem duplicidade e chaves explicitamente fictícias. O carrinho inicial permanece vazio, conforme o estado inicial do Prompt 12.
8. Um comando npm documentado recria a base local a partir dos scripts de esquema e massa, em caminho conhecido, sem etapas manuais ocultas. A recriação substitui somente o arquivo SQLite gerado e nunca apaga diretórios ou arquivos fora desse alvo; o banco binário gerado não se torna fonte da verdade nem precisa ser versionado.
9. Há testes automatizados reais, executados contra um banco temporário ou isolado, que comprovam: criação das 13 tabelas; inserção da massa; `PRAGMA foreign_key_check` sem violações; consultas de catálogo/compatibilidade, pedido/itens/total e biblioteca/chaves; e rejeição dos casos de integridade do AC 4. Os testes não dependem de ordem anterior nem alteram o banco demonstrativo versionado/gerado.
10. As consultas de evidência demonstram pelo menos: os dois produtos e suas plataformas compatíveis; quantidade `2` e total `10480` do pedido; pagamento aprovado; e os dois itens da biblioteca com loja e chave fictícia. Os resultados observados são registrados, sem valores presumidos.
11. O `README.md` explica pré-requisitos, arquivos de banco, comandos de inicialização, recriação, teste e consultas manuais, além de distinguir claramente scripts-fonte, arquivo SQLite gerado e dados fictícios. Um integrante deve conseguir reproduzir a base a partir de um clone e do lockfile.
12. A entrega não adiciona API, servidor HTTP, endpoint, Express, integração com Mercado Pago, autenticação persistente nem integração do Expo com SQLite. Também não altera as regras de estado em memória concluídas na Story 1.3; esses pontos ficam para o Prompt 15 ou para histórias futuras já identificadas.
13. `npm run lint`, `npm run typecheck`, `npm test` e `npm run build` continuam aprovados, e os novos comandos de banco também terminam com sucesso. Resultados, limitações e falhas reais são registrados no Dev Agent Record e em `docs/evidence/prompt-14/README.md`.
14. Antes do handoff, todas as tasks executadas são marcadas, o Change Log e as Completion Notes são atualizados e a File List registra exatamente os arquivos criados ou modificados, preservando mudanças preexistentes fora do escopo.

- Um usuário possui no máximo um carrinho e uma biblioteca; um pedido possui no máximo um pagamento; um produto não se repete no mesmo carrinho ou biblioteca. Chave é opcional por aquisição e única. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#4-relacionamentos-e-cardinalidades`]

Isso permite a FK simples e única de `item_biblioteca.item_pedido_id`, sem perder a cardinalidade aprovada. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#6-dicionário-de-dados-resumido`]

### Integridade e limites da camada SQL

- `PRAGMA foreign_keys = ON` é por conexão no SQLite; por isso deve aparecer tanto no inicializador quanto no bootstrap dos testes. `PRAGMA foreign_key_check` deve retornar zero linhas na base criada. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#7-regras-de-integridade`]
- Constraints devem cobrir regras locais de coluna/linha e unicidades. As quatro invariantes entre tabelas do AC 5 pertencem à transação da API/serviço do Prompt 15; nesta story, a seed apenas deve respeitá-las e a documentação deve torná-las explícitas. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#7-regras-de-integridade`]
- Pais com histórico (`usuario`, `produto`, `pedido`) não podem ser removidos quando referenciados. `CASCADE` cabe somente aos dependentes transitórios aprovados, como itens de um carrinho removido. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#7-regras-de-integridade`]
- Não definir o vocabulário externo do Mercado Pago nem histórico de tentativas: o Prompt 13 adiou essas decisões ao Prompt 15. A seed pode usar apenas os estados já aprovados (`PENDENTE`, `APROVADO`, `RECUSADO`, `ERRO`). [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#9-decisões-adiadas`]

### Estado real e abordagem de ferramentas

- Ambiente observado na elaboração: Node.js `v22.18.0`, npm `11.5.2`, SQLite CLI `3.44.4`; `node:sqlite` está disponível neste Node, com aviso experimental. O executor deve confirmar as versões novamente e registrar diferenças.
- O projeto não possui dependência SQLite no `package.json`. A implementação deve preferir a menor solução que funcione no ambiente e mantenha o SQL executável diretamente; qualquer nova dependência exige justificativa e atualização coerente do lockfile.
- O projeto já usa `node:test`. Os novos testes devem integrar esse executor, e `npm test` precisa incluir a suíte existente e `tests/database.test.mjs`.
- Não existe `docs/architecture/` nem `docs/framework/` neste checkout, apesar dos caminhos configurados no AIOX. As fontes de verdade desta story são o Prompt 14, o modelo aprovado do Prompt 13, o consolidado do Prompt 12, a Story 1.3, `AGENTS.md`, a Constitution e o estado real do repositório.
- ClickUp está indisponível (`mcp.enabled: false`) e CodeRabbit não está habilitado; o acompanhamento é local e a revisão de qualidade é manual.
