## Story

**Como** equipe de desenvolvimento do PixelVault,  
**quero** disponibilizar uma API Node mínima que consulte o SQLite local e exponha uma fronteira de pagamento segura em modo simulado,  
**para que** a base técnica do protótipo possa ser executada, demonstrada e testada sem credenciais reais ou cobrança, deixando a integração de teste com o Mercado Pago claramente delimitada para continuidade.

## Contexto e valor

Esta story conclui a parcela de API de `HT-02` e materializa o Prompt 15 sobre a base aprovada nos Prompts 13 e 14. O incremento é backend-first e executável por CLI. Ele demonstra saúde, leitura do catálogo local, criação simulada de pagamento para um pedido existente e consulta da biblioteca persistida, preservando a separação `UX-10` entre produto, loja de ativação, plataforma cloud e compatibilidade.

O modo simulado é obrigatório e deve funcionar sem qualquer segredo. A integração real ou de teste com o Mercado Pago não é requisito de conclusão: antes de escrever código relacionado ao provedor, o executor deve consultar e registrar a documentação oficial vigente. Se não houver credenciais de teste explicitamente fornecidas e autorizadas, nenhuma chamada externa será implementada ou alegada. O aplicativo Expo continua usando seu estado local; conectá-lo à API permanece fora desta story.

## Acceptance Criteria

1. Existe um backend Node executável por comando npm documentado, com organização mínima e separação entre composição HTTP, acesso SQLite e serviço/adaptador de pagamento. O processo inicia com código de saída não zero e mensagem útil quando o banco ou a configuração obrigatória não puderem ser abertos.
2. `GET /health` responde `200` em JSON e identifica, no mínimo, que o serviço está disponível e qual modo de pagamento está ativo. A rota não depende de chamada externa nem expõe caminhos locais, segredos ou stack traces.
3. `GET /api/products` consulta o SQLite criado pelo Prompt 14 e responde somente com os dados necessários ao catálogo: identidade, nome, tipo, preço em centavos, descrição, loja de ativação e plataformas cloud compatíveis. A resposta preserva `UX-10`, não duplica produtos por plataforma e possui ordem determinística.
4. `GET /api/users/:userId/library` consulta a biblioteca local e retorna os produtos, loja e chave fictícia quando aplicável; usuário inexistente e biblioteca vazia são diferenciados por respostas HTTP documentadas. A rota não implementa autenticação ou sessão e essa limitação fica explícita.
5. `POST /api/payments` possui contrato documentado e mínimo: recebe JSON com `pedidoId`, nunca recebe número de cartão, nome impresso, CVV, validade, token real ou total informado pelo cliente. O servidor localiza o pedido e seus itens no SQLite e deriva o valor exclusivamente de `pedido.total_centavos` após validar que a soma dos snapshots coincide com o total e que o pedido não está vazio.
6. Sem configuração de credenciais, a operação do AC 5 usa obrigatoriamente o adaptador `simulated`. A resposta identifica `mode: "simulated"`, `pedidoId`, `paymentId`, `status`, `valorCentavos` e uma referência inequivocamente fictícia; os estados internos permanecem limitados a `PENDENTE`, `APROVADO`, `RECUSADO` e `ERRO`, conforme o schema aprovado.
7. O fluxo simulado é transacional e idempotente: o pagamento persiste com valor igual ao pedido; apenas `APROVADO` pode materializar os itens na biblioteca; repetir a mesma operação para o mesmo pedido não cria segundo pagamento, item duplicado ou nova chave. Falhas provocam rollback e resposta de erro sem deixar estado parcial.
8. A camada de pagamento depende de um contrato interno substituível, sem espalhar detalhes do Mercado Pago pelas rotas ou pelo acesso ao banco. O modo real/teste, se não estiver pronto, permanece desabilitado e retorna erro de configuração controlado em vez de fazer fallback silencioso ou simular uma resposta apresentada como externa.
9. Antes de implementar qualquer adaptador do Mercado Pago, o executor registra em `docs/evidence/prompt-15/README.md` a data da consulta e links para páginas oficiais vigentes sobre a operação escolhida, credenciais de teste, autenticação, idempotência e respostas/erros. Nenhum SDK, endpoint externo, cabeçalho, campo ou mapeamento do provedor é inventado. Na ausência dessa pesquisa ou de credenciais de teste autorizadas, somente o adaptador simulado é implementado.
10. Há testes reais que iniciam a API em porta isolada e banco temporário, fazem requisições HTTP e cobrem: saúde; catálogo e compatibilidades; biblioteca existente, vazia e usuário inexistente; pagamento simulado aprovado; pedido inexistente; corpo ausente ou inválido; total inconsistente; repetição idempotente; rollback; rota inexistente e ausência de dados financeiros/segredos nas respostas e no banco.
11. O README documenta pré-requisitos, inicialização/recriação do SQLite, execução da API, variáveis permitidas sem valores secretos, endpoints com exemplos de requisição/resposta, modo simulado, comandos de teste e limitações. Um clone com o lockfile consegue executar a demonstração sem conta no Mercado Pago.
12. A entrega não integra o aplicativo Expo à API, não implementa autenticação persistente, CRUD administrativo persistente completo, webhook, reembolso, estorno, conciliação, retentativa automática ou pagamento real. As pendências de `HU-12` a `HU-15`, incluindo autenticação/autorização, integração de teste ponta a ponta e persistência móvel, são registradas para refinamento e priorização na Sprint 2.
13. O projeto permanece no Expo SDK 54; nenhuma atualização incompatível do Expo ou correção forçada de dependências transitivas é realizada para implementar o backend. Dependências Node novas, se indispensáveis, são justificadas e registradas no lockfile; nenhuma biblioteca é adicionada apenas por conveniência.
14. O teste específico da API, `npm run lint`, `npm run typecheck`, `npm test` e `npm run build` terminam com sucesso. Antes do handoff, checkboxes, Change Log, Dev Agent Record, Completion Notes e File List refletem exatamente o trabalho executado, e os resultados reais ficam em `docs/evidence/prompt-15/README.md`.

## Contrato HTTP mínimo

| Método e rota | Entrada | Sucesso | Falhas mínimas |
|---|---|---|---|
| `GET /health` | Nenhuma | `200` com `status` e `paymentMode` | `500` controlado somente se o serviço não puder avaliar a própria disponibilidade. |
| `GET /api/products` | Nenhuma | `200` com lista do catálogo e relações `UX-10` | `500` controlado para falha local de leitura. |
| `GET /api/users/:userId/library` | `userId` textual na rota | `200` com lista, inclusive vazia para usuário existente | `404` para usuário inexistente; `400` para parâmetro inválido. |
| `POST /api/payments` | JSON `{ "pedidoId": "..." }` | `200` ou `201`, conforme criação ou reutilização idempotente, com contrato do AC 6 | `400` corpo inválido; `404` pedido inexistente; `409` invariante de negócio violada; `503` modo externo solicitado mas não configurado; `500` falha inesperada sanitizada. |

Todos os corpos são JSON. A implementação deve documentar a escolha entre `200` e `201` de modo determinístico e manter o mesmo contrato nos testes. O modo é configuração do servidor, não um valor confiado ao corpo da requisição.

### Dados e invariantes

- O modelo físico possui exatamente 13 tabelas. IDs são textuais e moeda usa centavos inteiros. `pagamento.pedido_id` é único e seu status aceita `PENDENTE`, `APROVADO`, `RECUSADO` ou `ERRO`. [Source: `documentos/PixelVault_Script_SQL_e_Banco_Local.md#4-estrutura-física-do-banco`; `database/schema.sql`]
- A camada de serviço deve validar total do pedido pela soma de `item_pedido`, manter o valor do pagamento igual ao pedido e inserir biblioteca somente depois de aprovação. O schema deixa essas regras deliberadamente fora de triggers. [Source: `documentos/PixelVault_Script_SQL_e_Banco_Local.md#5-1-invariantes-reservadas-ao-prompt-15`]
- O modelo assume no máximo um pagamento por pedido; nova tentativa atualiza/reutiliza esse registro. Biblioteca e chave precisam permanecer idempotentes. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#2-premissas-de-modelagem`; `documentos/PixelVault_Modelo_de_Dados_e_DER.md#7-regras-de-integridade`]
- Dados de cartão, nome impresso e outros dados financeiros nunca entram no banco. O checkout atual também não preserva os valores digitados. [Source: `documentos/PixelVault_Modelo_de_Dados_e_DER.md#2-premissas-de-modelagem`; `documentos/PixelVault_Artefatos_Consolidados_Prompts_10_a_12.md#7-checkout-e-pedido-simulado`]
