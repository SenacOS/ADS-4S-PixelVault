## Story

**Como** usuário do PixelVault,  
**quero** recuperar o catálogo e meus dados demonstrativos após reabrir o aplicativo e consultar o catálogo disponível no backend,  
**para que** a experiência não dependa exclusivamente do estado em memória nem perca dados quando a rede estiver indisponível.

## Contexto e valor

Esta story inicia o item 2.1 da segunda entrega e a parte de persistência de `HU-13`, sobre o backend da Story 2.3. O aplicativo atual usa `useState` para catálogo, carrinho, pedido e biblioteca, sem consumir a API. A aula 07 apresenta SQLite no dispositivo e o servidor como apoio à sincronização. O incremento entrega a base local e a leitura remota do catálogo; não declara concluídas a sincronização bidirecional nem as histórias `HU-12` a `HU-15`.

O usuário retirou o dashboard do escopo e definiu que o pitch será um vídeo. Nenhum desses artefatos é implementado nesta story. A exportação JSON é um item separado e permanece para refinamento posterior.

## Acceptance Criteria

1. O aplicativo permanece no Expo SDK 54 e utiliza `expo-sqlite` compatível com essa versão para persistência no dispositivo. O executor consulta a documentação versionada antes do código e registra versão, instalação e fontes. Não se reutiliza `node:sqlite` no bundle React Native.
2. O catálogo, incluindo compatibilidades e alterações administrativas locais, é restaurado após reinicialização. A primeira utilização possui dados demonstrativos utilizáveis mesmo sem API disponível. Catálogo vazio confirmado é distinguido da ausência de dados persistidos.
3. Carrinho, biblioteca e último pedido demonstrativo são persistidos e restaurados por identidade de usuário demonstrativo. Alternar entre as contas demonstrativas não revela os dados de outra conta. Esses registros permanecem explicitamente demonstrativos, sem afirmar autenticação real ou compra aprovada pelo provedor.
4. A inicialização aguarda a leitura da persistência antes de permitir alterações que poderiam sobrescrever os dados restaurados. Escritas preservam sua ordem e uma falha de leitura/escrita apresenta mensagem sem informar falsamente que os dados foram salvos.
5. O aplicativo consome `GET /api/products` por um cliente HTTP separado das telas, com URL configurável, validação do status/corpo e limite de espera. A transformação do contrato preserva IDs, preço em centavos convertido corretamente, loja e plataformas, sem confundir loja de ativação com cloud.
6. Uma resposta válida do catálogo pode atualizar o cache local; falha de rede, timeout, HTTP ou contrato preserva os dados disponíveis e permite continuar usando o aplicativo offline. Alterações administrativas locais ainda não enviadas não são apagadas por atualização remota, inclusive se uma requisição já estava em andamento.
7. Nenhuma senha, sessão, token ou dado do formulário financeiro é escrito no armazenamento persistente. O cadastro e o login seguem demonstrativos em memória; a persistência desta story não substitui `HU-12`. Dados financeiros do checkout continuam sendo descartados após a demonstração.
8. A versão web permanece executável. Se usar adaptador específico de armazenamento, ele implementa o mesmo contrato funcional e sua diferença em relação ao SQLite nativo é documentada e testada; não se alega validação SQLite móvel com evidência apenas web.
9. Existem testes que comprovam reabertura da persistência, recuperação do catálogo/compatibilidades, isolamento por usuário, proteção contra sobrescrita remota, tratamento de rede/contrato inválido e ausência de dados sensíveis. A integração usa a API real com banco e porta isolados quando aplicável.
10. `npm run lint`, `npm run typecheck`, `npm test` e `npm run build` passam. Resultados efetivamente executados, limitações nativas e arquivos alterados são registrados na story e nas evidências. Nenhum teste não executado é declarado aprovado.
